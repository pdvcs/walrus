Estate map

An always-on Cloud Run service serves metadata and ranged downloads, backed by Cloud SQL and a GCS bucket. Work too long for a request runs as Cloud Run Jobs; Cloud Scheduler wakes the recurring work and Cloud Monitoring watches it.

Compute

Cloud Run service — walrus-api

The always-on HTTP face. It serves the public metadata API, ranged artifact downloads, health and docs; the authenticated operator UI under /admin/v1; and the machine-only /internal routes that Cloud Scheduler calls. It scales between one and four instances, which is not an arbitrary ceiling: the maximum is bounded by the Cloud SQL connection budget (see below), and the one-instance floor keeps the service responsive instead of cold on the first request. On-demand syncs run inside the service with a single transform slot, so it pins 1 GiB rather than the 512 MiB default.

Cloud Run Jobs — walrus-sync and walrus-vuln-backfill

Long-running work runs as Jobs, each in its own container with no request to outlive. walrus-sync is triggered six-hourly by Cloud Scheduler for the whole fleet; it discovers new releases, downloads and verifies them, applies any configured archive transform, stores the result in GCS, and prunes per the retention policy. It pins 2 vCPU and 2 GiB because two transforms can run at once, each holding roughly 500 MiB of link cache. The API also launches it directly, with --package/--job-id overrides, for an operator's "sync now" on one package — that used to run detached inside the service itself, which meant a large enough download (2+ GB across a handful of platform artifacts, say) could still be transferring when Cloud Run's CPU throttling and instance-recycling decided the service looked idle and pulled the container out from under it, silently, until the next boot's startup recovery marked the job "interrupted by restart". Running it as a Job instead gives it the same guarantee the scheduled walk already had: its own container, no response to outlive. walrus-vuln-backfill is launched the same way, with a --job-id override, when a package needs its historical CVEs fetched. Its 24-hour timeout and 1 GiB sizing reflect a workload that streams one page of NVD results at a time and is rate-limited upstream rather than CPU-bound.

A sync can transfer tens of gigabytes — onboarding a single IDE package has meant 25.8 GB across 16 artifacts. That is why it is a Job and why its timeout is six hours rather than the 30-minute ceiling of a Scheduler HTTP call.

Data stores

Cloud SQL — walrus-postgres

Postgres 18 on the smallest Enterprise tier, reachable only through the Cloud SQL Auth Proxy from the mounted /cloudsql socket. There are no authorised networks and no public application path. It holds catalogue state, jobs, audit history, vulnerability associations and artifact provenance. It is the source of truth.

Cloud Storage — the artifact bucket

Cached release binaries, some stored in a walrus-produced transformed form. It uses uniform bucket-level access, and Terraform is configured not to delete it on teardown (force_destroy = false), so it and the Terraform state bucket outlive terraform destroy.

Artifact Registry

A single Docker repository named walrus. Each deploy builds walrus-api:<git-sha> and pushes it; all three workloads run that same image, which is why a deployment verifier asserts their tags match. A partial deploy that updates the Jobs but not the service is a real failure mode.

The connection budget

Four numbers bound how many Postgres connections the estate can hold, and they move together:

service_db_pool_max × cloud_run_max_instances + job_db_pool_max × 2 ≤ db_max_connections − db_reserved_connections

With the defaults that is 3 × 4 + 4 × 2 = 20 ≤ 25 − 5. The invariant is enforced by a Terraform precondition, so an over-subscribed configuration fails at plan time rather than at three in the morning. The lesson behind it: raising the Cloud Run instance ceiling without raising the database tier does not scale the service up, it exhausts Postgres and turns a scale-up into an outage. The defaults size a test environment; production should raise the Cloud SQL tier and all four numbers together.

Scheduled jobs

Cloud Scheduler holds six jobs, all in UTC. Five call back into the API over OIDC using the walrus-scheduler service account; the package sync instead asks the Cloud Run Jobs API to start walrus-sync, authenticated with an OAuth token because the target is a Google API. That is one of two ways walrus-sync gets started — the other is walrus-api itself, as the walrus-api service account rather than walrus-scheduler, with a container-argument override naming one package, when an operator asks for that package right now instead of waiting for the next six-hourly tick.

Scheduler job Schedule (UTC) Target Purpose
walrus-sync 0 */6 * * * Cloud Run Job walrus-sync via :run Full package sync: discover releases, download, transform, retain.
walrus-vuln-sync-nvd 20 */2 * * * POST /internal/vuln-sync/nvd Incremental NVD ingestion on its cursor. Every two hours, because NVD changes constantly.
walrus-vuln-sync-kev 40 7 * * * POST /internal/vuln-sync/kev CISA KEV catalogue, once a day.
walrus-vuln-sync-osv 10 8 * * 1 POST /internal/vuln-sync/osv Weekly OSV cross-check, Mondays.
walrus-vuln-sync-cvss 10 9 * * * POST /internal/vuln-sync/cvss CVSS enrichment repair pass. Fills missing scores in a bounded walk (default 150 CVEs); a fresh score can newly block a download, which is intended (ADR-002).
walrus-vuln-backfill-auto 50 6 * * * POST /internal/vuln-backfill/auto Sweeps for newly tracked packages whose CVE history was never fetched, and launches walrus-vuln-backfill for each (ADR-003). Incremental sync is cursor-based and structurally blind to a package's past.

The minutes are offset deliberately. Package sync is on the hour, NVD at :20, cvss at :10 the next day, and the auto-backfill sweep at :50 after a scheduled NVD tick, so the sources do not contend for the same advisory lock. The retry backoff on the vulnerability jobs is 600 seconds for the same reason: a retry should land after a contended lock has been released, not bounce straight off it again.

Credentials and secrets

All runtime secrets live in Secret Manager and are mounted as references, never as literal values. Two of them are optional, and their absence changes throughput rather than correctness.

Secret Consumed by Notes
walrus-database-url required all three workloads The Postgres DSN, pointing at the /cloudsql socket.
walrus-session-secret required walrus-api Signs operator session cookies.
…-secret-previous required walrus-api Accepts sessions signed before a rotation.
walrus-admin-password required walrus-api Built-in admin provider; a strawman for an enterprise directory.
walrus-nvd-api-key optional service + both Jobs Raises NVD from 5 to 50 requests / 30 s. Keyless is supported; a backfill goes from minutes to hours.
walrus-github-token optional walrus-sync only Raises GitHub from 60 to 5,000 requests / hour. Mounted only on the one workload that calls api.github.com.

The optional secrets are declared unconditionally so their IAM bindings and rotation paths exist from the first apply, but a secret version is written only when the corresponding environment variable is supplied. A secret reference with no version is a hard deploy failure, so deploy.sh derives the mount flag from whether it actually populated one.

Identity and access

walrus-api

Runs the service and both Jobs. Holds GCS Object Admin on the artifact bucket, Cloud SQL Client, Secret Accessor on the six secrets, and a custom job-runner role (run.jobs.run + runWithOverrides) scoped to each Job individually — backfill and sync. The custom role exists because the API only needs to start those two Jobs, with a container-argument override, and nothing more.

walrus-scheduler

What Cloud Scheduler acts as. Holds run.invoker on the API service for the OIDC /internal calls, and run.invoker on the sync Job to start it. Invoking a service and executing a Job are separate permissions.

allUsers

Public run.invoker on the API service, which is what makes /api/v1, /download, health and docs reachable. It is not an authorisation bypass: /internal verifies OIDC audience, expiry and principal, and /admin is guarded by provider auth.

Observability

The estate distinguishes two tiers. Tier 1 sends email and is deliberately narrow, because paging a human for a transient failure teaches them to ignore the channel. Tier 2 is the surface an operator looks at, and it never notifies.

Tier 1 — alerts

Cloud Run error, scheduler job failed, vulnerability sync degraded (more than one failure in four hours), automatic CVE backfill exhausted, and a deliberate informational alert when versions become undownloadable. That last one is walrus working correctly; it exists so the block is not discovered as a mystery build failure.

Tier 2 — dashboard

The "Walrus operations" dashboard charts vulnerability sync failures by source, scheduler invocation failures by job, API requests by response class, and Job executions by result. Two of those charts are fed by log-based metrics, because Cloud Scheduler publishes no metric at all.

Deploying and tearing down

bash infra/scripts/deploy.sh runs the TypeScript build, builds and pushes a git-SHA-tagged image, writes the runtime secrets, imports any pre-existing secrets into Terraform state, applies the full plan, and finally rolls the new image onto the Cloud Run service. Terraform owns everything except the container image, which it ignores so that routine deploys are not Terraform runs.

bash infra/scripts/teardown.sh confirms, lowers deletion protection on Cloud SQL and the Jobs, and destroys the Terraform-managed resources. The Terraform state bucket and the artifact bucket are deliberately left behind.

verify-deployment.sh asserts the invariants the tickets claim: healthy service, all six scheduler jobs enabled and firing, matching image tags across the three workloads, correct memory/heap/pool sizing, mounted secrets, alert policies with severities, the dashboard and log metrics, auth rejection on /internal, and — with --full — that served bytes hash to their published digests.
